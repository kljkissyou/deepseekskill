# 经验总结：交付文件卡片「打开真实文件 / 资源管理器定位」

日期：2026-09-23　涉及：`_dsh-plugin\dsh-open-in-explorer`、DSH Web 交付卡片、Windows GUI 启动器
适用：以后再做「DSH 里点一下 → 调起系统程序」这类需求，先读这份。

---

## 1. 问题现象

1. 交付文件卡片点「打开」→ 打开右侧侧边栏预览，而不是打开真实文件。
2. 卡片空白处 / `⌄` 菜单「在文件资源管理器中显示」→ 点了没反应，资源管理器窗口不弹。
3. 之前把 `dsh-open-in-explorer` 插件回滚掉后，所有「调起资源管理器」的行为一起失效。

## 2. 根因（三层叠加，缺一层都修不好）

### 2.1 GUI 启动器被强加 windowsHide:true（窗口不显示的真凶）

- DSH Desktop 启动 Harness 时加载 `resources/windows-child-process-hide.mjs`，
  给 `child_process.spawn` 打补丁：**调用方没显式写 `windowsHide` 就一律改成 `true`**。
- `windowsHide:true` → `CreateProcess` 带 `CREATE_NO_WINDOW`。对 `explorer.exe` / `open`
  这类 GUI 子系统程序，结果是：**进程起来了、接口返回 `{"started":true}`、窗口永远不显示**。
- 典型受害代码：`dsh-better-sidebar` 的 `launchExternal()`
  `spawn(spec.command, spec.args, { detached: true, stdio: "ignore" })`，
  它的 reveal 分支就是 `explorer.exe /select,<path>`。
- 启动日志里有这条可自查：`[harness-node] windowsHide enforcement enabled for child processes`。

**修法**：不要改第三方源码（升级会被覆盖），在插件宿主里包一层 `child_process.spawn`：

```js
const GUI_LAUNCHERS = new Set(['explorer.exe', 'explorer', 'open', 'xdg-open'])
function patchedSpawn(command, args, options) {
  if (GUI_LAUNCHERS.has(baseName(command))) {
    return original.call(this, command, args, { ...options, windowsHide: false })
  }
  return original.call(this, command, args, options)
}
childProcess.spawn = patchedSpawn
syncBuiltinESMExports()   // 关键：否则 import { spawn } 的实时绑定还是老函数
```

补丁"见到显式值就放行"，所以只对白名单命令显式补 `false`，其它命令完全不碰（git 等仍走 `true`）。
自检：`node _dsh-plugin\verify-spawn-patch.mjs`（6 项，含 `spawn(command, options)` 重载与 macOS 分支）。

### 2.2 卡片 DOM 默认行为：「打开」按钮 = 预览

`@deepseek-ai/dsh-client-ui-deliverables` 的 `PresentedFileCard`（文件在 App 包内）：

```
<div data-presented-file>
  <button class="…cardPreview" title="<绝对路径>">        ← 整卡覆盖层，onClick=onPreview
  <div class="…fileBody">
    <div class="…split">
      <button class="…open">打开</button>                  ← 也是 onClick=onPreview
      <button class="…chevron">⌄</button>                  ← 菜单：用默认应用打开 / 在文件资源管理器中显示
```

- 真正的系统动作藏在 `⌄` 菜单：`id:open` → 官方 `/api/present.open`（默认应用打开）、
  `id:reveal` → 同路由带 `action=reveal`（资源管理器定位）。
- 拦截要点：必须用 **document 捕获阶段**（`addEventListener('click', fn, true)`），
  比 React 挂在 root 上的合成事件更早；然后 `preventDefault + stopPropagation + stopImmediatePropagation`
  才能真正吃掉这次点击。
- `⌄` 菜单是 **portal 到 body** 的，菜单点击时 `closest('[data-presented-file]')` 找不到卡片。
  做法：点卡片/⌄ 时先记住 `lastCard = { path, rect, at }`，菜单项点击再用
  「15 秒内 + 420px 内」双重约束关联回来。

**修法**：插件自己做两个动作路由，绕开官方链路（官方在"主机没有桌面"时只会把卡片标成"打开失败"）。

### 2.3 类名带构建哈希，选择器必须模糊匹配

实际类名是 `nyYjTG_cardPreview` / `nyYjTG_open` / `nyYjTG_split`（哈希前缀随构建变）。
只能用键名子串匹配：`button[class*="cardPreview"]`、`button[class*="open"]`、`[class*="split"]`，
并留结构化兜底（如"split 容器里的第一个 button"）。DSH 大版本升级后先看 `diag.log` 里的 `census`
（会报 cardCount / previewCount / openButtonCount）确认选择器还有效。

## 3. 最终实现（可复用结论）

| 动作 | 命令（Windows） | 说明 |
|---|---|---|
| 打开真实文件 | `explorer.exe <path>` | Explorer 对文件参数走 ShellExecute，等同双击。实测 `explorer.exe …\测试文件.txt` 拉起 Notepad |
| 资源管理器定位 | `explorer.exe /select,<path>` | 打开所在文件夹并选中该文件（`/select,` 后面**不能有空格**） |

三条硬要求：`detached: true` + `stdio: 'ignore'` + **`windowsHide: false`**；spawn 后 `child.unref()`。

- 路由：`POST /open-in-explorer/open`、`POST /open-in-explorer/reveal`、`POST /open-in-explorer/diag`。
- 客户端分流：整卡覆盖层 → reveal；`…open` 主按钮 → open；`⌄` 菜单 reveal 项 → **官方照跑 + 本插件兜底**
  （reveal 重复无害，Explorer 会聚焦同一窗口）；`⌄` 菜单的"用默认应用打开"本次**没接管**
  —— 因为 open 不能"官方+兜底"同时跑，否则文件会开两份。
- 免界面自检入口（比重启后让用户找按钮可靠得多）：
  `GET /open-in-explorer/test`（定位）、`GET /open-in-explorer/test-open`（默认应用打开）。
- 改完**必须完整重启 DSH Desktop**：宿主半边只在启动时加载，客户端脚本在页面加载时注入。

## 4. 这次踩到的环境坑（与业务无关，但每次都会咬人）

1. **命令沙箱写权限**：本会话的 pwsh 只能写 `E:\Deepseek`（工作区）和会话临时目录
   `%TEMP%\dsh-xxxx`；写 `DSH_HOME`（`AppData\Roaming\dsh-desktop\harness`）、桌面、`E:\` 根
   一律 `EPERM / UnauthorizedAccessException`。
   → 凡是要落到 `DSH_HOME` 的部署，必须让用户跑；本次交付了一个幂等一键脚本
   `_dsh-plugin\deploy-open-in-explorer.cmd`（备份 → 整包复制 → 追加挂载 → 哈希/YAML 校验）。
2. **pwsh 写文件会剥掉行首 TAB**：用 here-string + `WriteAllText` 写出的 `.js`，行首 tab 全部丢失
   （所以历史上那版 `client.js` 是"平铺"的）。→ 统一用 4 空格缩进；
   若已经写坏，可只重排行首空白，再用 `s.replace(/\s+/g,'')` 做 **token 恒等校验**确认没改语义
   （本次就是这样修好 client.js / index.js 的）。
3. **会话日志是多帧 zstd**：`session.v3.jsonl.zstd` 由多个 zstd frame 追加而成，
   Node 的 `zstdDecompressSync` **只解第一帧**（本次只拿到 206 字节的 header）。
   做法：按魔数 `28 B5 2F FD` 切帧逐帧解；只看"谁交付了什么"更快的是读
   `storages\session_projcache\sessions\session-*.json`。
4. **HTTP 自检会被认证栅栏挡住**：`http://127.0.0.1:43129/...` 除本插件路由外一律 401，
   所以"401"不能证明路由存在；**404 才能证明路由不存在**。token 在 `logs\harness.log`
   的 `dsh web: http://127.0.0.1:43129/?token=...` 里。
5. **中文 .ps1 编码铁律（旧坑，重温）**：无 BOM + LF 的含中文 `.ps1` 会被 PowerShell 5.1 错解
   （报 `Unexpected token '}'`，行号还偏）。写 `.ps1` 一律 BOM + CRLF。

## 6. 遗留问题

- `⌄` 菜单「用默认应用打开」仍走官方 `/api/present.open`；若实测不好用，按 reveal 的模式加 open 分流，
  但必须**阻止官方路径**（`stopImmediatePropagation`）并自己补关菜单，否则会开两份。
- 官方 present host 链路依赖 `@deepseek-ai/dsh-tool-present` 在 web profile 可见：
  当前 `profiles\web\node_modules\@deepseek-ai` 为空，启动日志一直有
  `profile inconsistency: … dsh-tool-present … not installed`。交付卡片 UI 能显示（客户端来自 App 包），
  但官方 open/reveal 路由是否可用未验证 —— 本插件自带路由正是为了不吃这条链路。
